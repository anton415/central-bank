# Архитектура: модули по бизнес-возможностям

## Контекст и решение

Проект развивается как модульный монолит: один репозиторий, одна Maven-сборка
и один процесс приложения. Границы будущих Maven-модулей определяются
бизнес-ответственностью и появляются вместе с работающими сценариями.

На этапе задачи #4 единственным модулем с кодом остаётся `application`.
Корневой `pom.xml` сохраняется как общий parent и reactor aggregator:
он управляет версиями, Java toolchain и проверками качества.

```text
central-bank/
├── pom.xml
├── application/
│   ├── pom.xml
│   └── src/
└── docs/
    └── architecture.md
```

Это решение заменяет исходный граф из
[задачи #2](https://github.com/anton415/central-bank/issues/2) и прежнего описания
в Wiki Architecture. Модули `organization-registry`,
`organization-registry-postgresql` и `ui-vaadin` удалены из скелета: они содержали
только POM-файлы и одинаковые проверки Java toolchain, без прикладного кода.
Актуальная структура для этого изменения описана на этой странице.

## Ответственность application

В задаче #4 модуль реализует точку входа, загрузку и проверку INI-конфигурации,
безопасное логирование, явное создание и связывание объектов (composition root),
жизненный цикл Jetty и стартовую Vaadin-страницу состояния.

Технические обязанности разделяются Java-пакетами внутри модуля. Например,
по мере реализации появляются пакеты `config`, `bootstrap`, `runtime` и `ui`
внутри `io.github.anton415.centralbank.application`. Пустые пакеты заранее
не создаются. Сейчас реализованы модель конфигурации, загрузчик INI, диагностика
его результата через SLF4J/Logback, жизненный цикл Jetty и обработчик `/health`.
`ApplicationMain` служит точкой входа и composition root: явно создаёт загрузчик,
обработчик и runtime. Maven запускает приложение в отдельной JVM через `exec:exec`.
Тесты проверяют конфигурацию, диагностику, HTTP-ответы, коды завершения,
прерывание ожидания и остановку JVM с освобождением порта.
Сохраняется проверка Java toolchain. Пакет `ui` содержит `StatusView` и
`StatusServlet`: composition root передаёт фабрику страницы, получающей только
название приложения. Servlet регистрирует маршрут `/` явно и создаёт отдельное
дерево компонентов для каждой страницы через точку расширения Vaadin Instantiator.
`/health` обрабатывается перед servlet-контекстом и сохраняет простой HTTP-контракт.
Клиентские ресурсы Vaadin подготавливаются на фазе Maven `process-classes`;
команда запуска и расположение публичных ресурсов описаны в README.

## Рост бизнес-модулей

Новый модуль появляется, когда есть конкретный бизнес-сценарий, собственная
ответственность и понятный публичный API. Например, реализация реестра
организаций может дать основание добавить `organization-registry`.

Такой модуль может содержать пакеты `api`, `domain`, `usecase`, `ui` и
`persistence`. Создаются только пакеты, необходимые текущему сценарию.
Vaadin и JDBC относятся к реализации соответствующей бизнес-функции;
отдельные Maven-модули для них автоматически не вводятся.

Правила зависимостей:

- `application` зависит от бизнес-модулей и явно собирает их компоненты.
- Бизнес-модули не зависят от `application`. Необходимые настройки и сервисы
  передаются через конструкторы или контракты, принадлежащие бизнес-модулю.
- Связи между бизнес-модулями вводятся по потребности через публичные контракты;
  циклические зависимости и доступ к внутренним классам другого модуля запрещены.
- Внутри бизнес-модуля UI и persistence зависят от контрактов и сценариев;
  бизнес-правила не импортируют Vaadin, Jetty или JDBC.
- Composition root создаёт объекты; бизнес-правила принадлежат бизнес-модулям.

## Последствия и проверка

Изменения одной бизнес-функции группируются в одном модуле. При этом Maven
проверяет зависимости между артефактами, но не обеспечивает направление импортов
между пакетами одного модуля. На текущем этапе это проверяется при review;
архитектурные тесты можно добавить с появлением таких границ в коде.

Сохраняются JDK 25, Maven Wrapper, JUnit, Checkstyle и транзитивный запрет
Spring, Hibernate и JPA. Общая команда проверки остаётся `./mvnw verify`.
Проверка Java toolchain сохраняется в `application`; будущие бизнес-модули
получат тесты своих реальных сценариев.
